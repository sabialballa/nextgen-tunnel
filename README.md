# Nextgen Tunnel — نسخهٔ آزمایشی

## اجرای منو روی سرور Linux

بدون نیاز به Go، این دستور را روی سرور اجرا کنید؛ برای نصب سرویس‌ها از کاربر root استفاده کنید:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/sabialballa/nextgen-tunnel/main/menu.sh)
```

اگر SSH بین سرورها بسته است، گزینهٔ **۱۰: Install separately without SSH: pairing codes** را روی هر دو سرور اجرا کنید: ابتدا ایران/listener یک کد دعوت می‌دهد؛ ترکیه/initiator آن را می‌گیرد و یک کد پاسخ می‌دهد که به ایران برمی‌گردانید. کلیدها و JSON خودکار ساخته می‌شوند. [راهنمای نصب با کد](docs/console-pairing.md).

گزینهٔ **۱: نصب سادهٔ هر دو سرور از SSH** نیز باقی است: فقط روی یکی از سرورها انتخابش کنید و نقش همان سرور و IP طرف مقابل را بدهید. اتصال root با SSH لازم است؛ اگر کلید SSH ندارید، خود SSH ممکن است یک‌بار رمز و تأیید اثرانگشت بخواهد. [راهنمای نصب از SSH](docs/easy-install.md).

نصب پیشرفته، وضعیت، تست اتصال و مدیریت جداگانهٔ تونل‌ها هم در [منو](docs/menu.md) باقی مانده‌اند. بازکردن منو چیزی نصب نمی‌کند.

## شروع تست از GitHub

روی Linux با Go 1.27.4 و Python 3، ابتدا تست محلی را اجرا کنید؛ این مرحله به تنظیم شبکه یا کلید سرور نیاز ندارد:

```sh
git clone https://github.com/sabialballa/nextgen-tunnel.git
cd nextgen-tunnel
mkdir -p dist
go build -trimpath -o dist/nextgen-tunnel ./cmd/nextgen-tunnel
go test ./...
python3 scripts/local_lab.py --binary ./dist/nextgen-tunnel --output ./dist/local-lab.json --seconds 1 --samples 50 --repetitions 2
```

برای اتصال دو سرور از [نصب ساده](docs/easy-install.md) استفاده کنید؛ مسیر دستی و پیشرفته در [راهنمای engine/site](docs/engine-site.md) باقی است. [GRE، VXLAN و IPIP](docs/overlays.md) نیز جداگانه قابل مدیریت‌اند. اطلاعات دسترسی سرورهای تست در مخزن نیست. این نسخه هنوز معیار پایداری UDP را پاس نکرده است؛ [نتایج واقعی تست](docs/STATUS.md) را ببینید.

افزونهٔ اختیاری [GRE، VXLAN و IPIP](docs/overlays.md) روی هر دو سرور نصب، هم‌زمان یک ساعت تست و پس از ریبوت واقعی هر دو سرور بازیابی شد. TCP بدون خطا بود؛ معیار تأخیر UDP در هیچ روش پاس نشد و برتری پایداری روشنی تأیید نشد. بستهٔ افزونهٔ۰٫۲٫۰ جدا از آرشیوهای rc3 است.

هستهٔ جدید Go در `cmd/nextgen-tunnel` و `internal/` قرار دارد: TCP/UDP، TLS 1.3 دوطرفه، QUIC DATAGRAM و مسیر جایگزین TLS/TCP. راهنمای آن در [NEXTGEN.md](NEXTGEN.md) و وضعیت تأیید قابلیت‌ها در [docs/STATUS.md](docs/STATUS.md) است. این نسخه برای آزمایش منتشر می‌شود و هنوز تأییدیهٔ Production یا مقاومت در برابر DPI ایران ندارد.

نسخهٔ `0.3.0-rc3` افزونگی مسیر برگشت را اصلاح می‌کند، اما آزمون یک‌ساعته و آزمون سبک ده‌دقیقه‌ای روی دو سرور همچنان معیار UDP را پاس نکردند. TCP تونل در آزمون سبک بدون خطا بود؛ مسیر مستقیم UDP نیز اختلال مستقل نشان داد. اشباع CPU ترکیه در آزمون سبک مشاهده نشد و محدودیت مقطعی زمان CPU ایران علت انحصاری ثابت‌شده نیست. [نتایج](docs/STATUS.md) و [راهنمای نصب](docs/engine-site.md). Production تأیید نشده است.

کد و راهنمای قبلی زیر حفظ شده‌اند. این دو مسیر استقرار مستقل‌اند؛ ابزار جدید هیچ مهاجرت خودکاری روی سرویس‌های قبلی انجام نمی‌دهد.

# gaming-tunnel (ابزار قبلی)

اسکریپت نصب یک ارتباط اختصاصی بین دو سرور Linux با WireGuard روی حامل ICMP، فوروارد محدود پورت‌های VPN، صف CAKE و تنظیم بافر دریافت حامل.

این بسته از تنظیمات آزمایش‌شده روی Ubuntu 22.04 و 24.04 استخراج شده است. پروتکل VPN کاربران را عوض نمی‌کند. مقدارهای MTU و پهنای‌باند «بهترین مقدار برای همه شبکه‌ها» نیستند؛ پروفایل مرجع همین پروژه‌اند.

## اجزا

- tunnelctl.py: مدیریت جفت‌سرور از طریق SSH با کلید و بررسی سخت‌گیرانه کلید میزبان.
- agent.py: نصب روی Linux، بکاپ محدود، Rollback زمان‌دار و مدیریت تست.
- runtime/: مانیتور، CAKE، بافر AF_PACKET و تست پایداری محافظت‌شده.
- deployment.example.json: فقط IPهای مستنداتی؛ هیچ رمز یا کلید واقعی ندارد.
- tests/: تست‌های اعتبارسنجی، تولید تنظیمات و محدوده Rollback.

## پیش‌نیازها

روی کامپیوتر مدیریت Python 3.10+ و OpenSSH لازم است. دو سرور باید Linux x86_64 با kernel 5.6+، systemd، WireGuard و قابلیت sch_cake باشند. پروفایل روی Ubuntu آزمایش شده است.

دسترسی root با SSH key و known_hosts تأییدشده لازم است. رمز SSH در فایل تنظیمات یا آرگومان اسکریپت قرار نمی‌گیرد. اثرانگشت میزبان‌ها را از کنسول معتبر ارائه‌دهنده تطبیق بدهید.

برای جلوگیری از بازکردن ناخواسته فایروال، نصب مرجع روی میزبان با policyهای INPUT/FORWARD غیر از ACCEPT متوقف می‌شود؛ فایروال سفارشی نیاز به ادغام دستی قوانین محدود دارد. قوانین nftables مستقل نیز ممکن است نیاز به بررسی اپراتور داشته باشند.

باینری udp2raw را جداگانه از منبع رسمی [پروژه اصلی](https://github.com/wangyu-/udp2raw) بگیرید و SHA-256 آن را از منبع معتبر بررسی کنید. این مخزن باینری ثالث را همراه خود منتشر نمی‌کند و از آدرس تصادفی دانلود/اجرا نمی‌کند.

## نصب جفت‌سرور

فایل نمونه را به deployment.json کپی و فقط اطلاعات عمومی دو میزبان و SSH alias/port را تنظیم کنید. این فایل و پوشه .private در Git نادیده گرفته می‌شوند.

    cp deployment.example.json deployment.json
    python3 tunnelctl.py audit deployment.json
    python3 tunnelctl.py deploy deployment.json --binary ./udp2raw --sha256 VERIFIED_SHA256 --install-deps
    python3 tunnelctl.py status deployment.json

گزینه install-deps فقط ابزارهای لازم را از مخزن سیستم نصب می‌کند؛ upgrade کامل یا restart سرویس‌های VPN انجام نمی‌دهد. اگر apt index قدیمی باشد نصب خطا می‌دهد؛ ابتدا آن را جداگانه به‌روز کنید.

مراحل deploy:

1. شناسایی میزبان‌ها و Listenerهای واقعی backend.
2. تولید کلید خصوصی WireGuard روی خود هر سرور؛ فقط کلید عمومی جابه‌جا می‌شود.
3. ایجاد کلید مشترک حامل داخل .private با مجوز محدود؛ نه در Git و نه در آرگومان پردازش.
4. بکاپ از منابع اختصاصی و فعال‌کردن Rollback خودکار ۱۵دقیقه‌ای.
5. نصب ابتدا exit و سپس entry، بدون تعویض default route.
6. تأیید data plane در هر دو جهت؛ سپس فعال‌کردن فوروارد پورت‌ها و مانیتور.
7. لغو Rollback زمان‌دار فقط بعد از موفقیت هر دو طرف.

نصب روی تانل موجودی که این ابزار مالک آن نیست متوقف می‌شود. برای ارتقای زنده ابزار فعلی یا مهاجرت سرویس‌ها طراحی نشده است. اجرای مجدد همان نصبِ مدیریت‌شده با تنظیمات یکسان، بی‌تغییر می‌ماند؛ تغییر تنظیمات مدیریت‌شده بدون برنامه مهاجرت رد می‌شود.

این بسته در همین مرحله روی سرورهای فعال پروژه دوباره deploy نشده است؛ بسته‌بندی کد و تست‌های آفلاین، معادل تست نصب انتهابه‌انتها روی VM تازه نیست.

## اتصال خودکار پس از روشن‌شدن سرور

نصب، سرویس‌های address، carrier، WireGuard، forwarding و تایمر monitor را برای بوت فعال می‌کند. حامل پس از sysctl و سرویس‌های فایروال موجود اجرا می‌شود؛ WireGuard پس از حامل و آدرس سرویس، و forwarding پس از آن‌ها اجرا می‌شود. خطای شروع حامل، WireGuard یا forwarding با تأخیر دوباره امتحان می‌شود. Restart خودکار فقط برای خطای سرویس است؛ اتصال موجود با daemon-reload قطع نمی‌شود.

    systemctl is-enabled gaming-address gaming-raw wg-quick@wg-game gaming-forward gaming-monitor.timer
    systemctl is-active gaming-address gaming-raw wg-quick@wg-game gaming-forward gaming-monitor.timer

ریبوت خودِ سرور اتصال کاربران را موقتاً قطع می‌کند. فعال‌بودن بوت و بررسی واحدها بدون ریبوت قابل تأیید است؛ آزمون واقعی چرخه ریبوت نیاز به زمان تعمیرات دارد. اگر فقط یک سرور روشن باشد، اتصال پس از در دسترس قرارگرفتن سمت دیگر دوباره برقرار می‌شود. بازنویسی دستی فایروال پس از بوت خارج از این ترتیب است و باید جداگانه ادغام شود.

## پورت‌ها و حفظ سرویس‌ها

UDP 500/4500/1701/34569 و Transport واقعی Listenerهای 46954 و 48320 تشخیص داده می‌شود. فوروارد تنها برای Listenerهای پیدا‌شده از همین allowlist است؛ سرویس جدید VPN یا کاربر جدید ساخته نمی‌شود.

DNAT/SNAT محدود به پورت‌های انتخاب‌شده است. IPهای داخلی سرویس ثابت‌اند تا مسیر برگشت مشخص باشد. SNAT آدرس عمومی اصلی کلاینت را از سوکت backend پنهان می‌کند. IPsec چندکاربره پشت یک NAT محدودیت‌های خودش را دارد و باید با کلاینت‌های واقعی تست شود.

L2TP بدون policy ورودی IPsec روی رابط تانل رد می‌شود. MSS فقط برای subnet و رابط‌های PPP تعیین‌شده و فقط برای MSSهای بزرگ‌تر کاهش می‌یابد؛ SYN و SYN-ACK هر دو پوشش داده شده‌اند.

هیچ حذف کلی برای GRE/WireGuard، سرویس، cron، routing، firewall یا دیتابیس اجرا نمی‌شود. پاک‌سازی تانل قدیمی نیاز به تعیین مالکیت، بکاپ و طرح مهاجرت جداگانه دارد؛ نام یک سرویس به‌تنهایی دلیل حذف آن نیست.

## پروفایل مرجع کارایی

- WireGuard MTU: 1360
- CAKE: مجموع 120Mbps در هر جهت با overhead=100 و rtt=100ms
- بافر دریافت اختصاصی AF_PACKET حامل: درخواست 8192KiB؛ Linux مقدار مؤثر 16MiB گزارش می‌کند.
- مانیتور: هر ۳۰ ثانیه؛ سه خطای متوالی و cooldown پنج دقیقه پیش از بازیابی حامل.
- سقف rmem_max فقط در صورت نیاز به مقدار کافی بالا می‌رود؛ مقدار پیشین بکاپ می‌شود. default buffer سایر سرویس‌ها تغییر نمی‌کند.
- default route، IRQ affinity و offload رابط فیزیکی تغییر نمی‌کنند.

بافر AF_PACKET با بافر UDP loopback فرق دارد. helper تنها سوکت AF_PACKET/SOCK_DGRAM متعلق به gaming-raw را از طریق pidfd_getfd پیدا می‌کند و SO_RCVBUF همان سوکت را تنظیم می‌کند. سوکت اصلی را نمی‌بندد و حافظه پردازش را دستکاری نمی‌کند. به root و Linux x86_64 نیاز دارد.

شماره carrier_id در حالت ICMP به معنی استفاده از TCP نیست. قوانین ICMP فقط بین دو IP عمومی اعمال می‌شوند؛ برای بررسی سلامت از IP داخلی سرویس استفاده کنید، نه Ping عمومی بین همان دو سرور.

## اصلاح اختیاری L2TP

به‌صورت پیش‌فرض تنظیمات VPN موجود و فایل‌های آن دست‌نخورده‌اند. فقط اگر چیدمان strongSwan/xl2tpd شما با پروفایل مرجع مطابقت دارد:

    python3 tunnelctl.py repair-l2tp deployment.json

این فرمان opt-in از ipsec.conf و options.xl2tpd بکاپ می‌گیرد، پیشنهاد AES256/SHA256/MODP2048 را کنار پیشنهادهای قبلی اضافه می‌کند، MTU/MRU پروفایل و keepalive=10/6 را می‌گذارد و ipsec update اجرا می‌کند. کاربران، PSKها و دیتابیس‌ها را نمی‌خواند/تغییر نمی‌دهد. در چیدمان سفارشی به‌جای اعمال حدسی خطا می‌دهد. MTU/MRU جدید با اتصال جدید PPP مذاکره می‌شود؛ فرمان VPN service را restart نمی‌کند.

## تست پایداری با محافظ توقف

iperf3 باید روی هر دو میزبان نصب باشد.

    python3 tunnelctl.py soak deployment.json --seconds 900 --tcp-mbit 20 --udp-mbit 1

هم‌زمان TCP و UDP در هر دو جهت اجرا می‌شود. تست با افزایش افت UDP، افت Ping، تأخیر، فشار CPU یا تغییر وضعیت حامل متوقف می‌شود؛ تنها jobهای تست متوقف می‌شوند. تست بار، تضمین عدم اثر روی تک‌تک کاربران نیست؛ از نرخ پایین شروع کنید.

listenerها فقط به IP تانل bind می‌شوند و deadline دارند. نتیجه‌ها در /var/lib/gaming-tunnel/bench/TRANSACTION روی سرورها می‌مانند. با وجود نتیجه مثبت، اتصال واقعی VPN و پایداری چندساعته باید جداگانه بررسی شوند.

## Rollback نصب

شناسه تراکنش در پایان deploy چاپ می‌شود:

    python3 tunnelctl.py rollback deployment.json --transaction TRANSACTION

فقط منابع اختصاصی همین نصب حذف/بازگردانده می‌شوند؛ هیچ flush کلی firewall یا XFRM وجود ندارد. مقدارهای قبلی forwarding و rmem_max نیز بازگردانده می‌شوند. برای rollback تولیدی، دسترسی مستقل SSH و کنسول ارائه‌دهنده را نگه دارید. این دستور خودِ تانل مدیریت‌شده را متوقف می‌کند؛ برای آزمایش روی کاربران فعال اجرا نکنید.

## اعتبارسنجی کد

    python3 -m unittest discover -s tests -v
    python3 -m py_compile tunnelctl.py agent.py model.py runtime/receive-buffer.py runtime/soak.py

تست‌ها به SSH یا root نیاز ندارند و هیچ سرویس شبکه را اجرا نمی‌کنند. خروجی Shell تولیدشده با bash -n بررسی می‌شود.

اعتبارسنجی ۲۰۲۶-۱۱-۱۵: هر ۱۶ تست و py_compile روی هر دو میزبان Ubuntu 22.04 و 24.04 پاس شدند. چرخه apply/activate/commit/rollback و شکست میانه نصب با فایل‌های موقت و فرمان‌های سیستمی شبیه‌سازی‌شده پوشش داده شده است. اجرای مجدد نصب بدون تغییر، شناسه Rollback نصب اصلی را حفظ می‌کند.

روی سرویس‌های فعال، ترتیب بوت با drop-in و daemon-reload اصلاح شد و systemd-analyze verify موفق بود. شمارنده Restart و PID حامل هنگام اعمال تنظیمات تغییر نکرد و در بررسی یک‌دقیقه‌ای هر جهت ۱۲۰ از ۱۲۰ پاسخ Ping رسید.

سپس در همان روز سرورها به‌ترتیب هلند و ایران واقعاً ریبوت شدند؛ تغییر Boot ID هر دو تأیید شد. تانل، فوروارد و همه backendهای VPN فعال پیش از ریبوت، خودکار برگشتند. بافر مؤثر 16MiB، CAKE، قوانین MSS و مانیتور نیز برقرار ماندند. بعد از بوت هر دو جهت Ping بدون افت بود؛ TLS سرویس Cisco از IP عمومی ورودی پاسخ داد و اتصال واقعی کاربر همراه با PPP/IPsec فعال تأیید شد. این آزمون، بازیابی تنظیمات عملیاتی موجود را تأیید می‌کند؛ نصب این بسته روی دو VM تازه هنوز آزمون انتهابه‌انتها نشده است.

## نتیجه میدانی پروفایل

در تست مرجع، هر جهت TCP=20Mbps و UDP=1Mbps به‌طور هم‌زمان برای ۱۵ دقیقه اجرا شد. پس از اصلاح بافر دریافت:

| معیار | ایران به هلند | هلند به ایران |
|---|---:|---:|
| TCP دریافتی | حدود 20Mbps | حدود 20Mbps |
| افت UDP | 1 از 703125 | 4 از 703125 |
| افت Ping | صفر | صفر |
| بازفرستادن TCP | 58 | 21 |
| Restart حامل | صفر | صفر |

آمار قبل از اصلاح، در جهت برگشت حدود 0.21% افت UDP و 2674 بازفرستادن TCP در اجرای کوتاه‌تر بود. این اعداد متعلق به یک مسیر و بازه‌اند؛ SLA، ظرفیت تضمینی یا ادعای zero loss نیستند.

اطلاعات عملیاتی واقعی، IPهای سرورها، رمزها، کلیدهای خصوصی، packet captureها و deployment-records همراه مخزن منتشر نمی‌شوند.
