# Security model and remaining audit gates

Both transports require TLS 1.3 and a certificate issued by the configured dedicated CA. Client verifies server name and chain; server verifies client chain, client EKU and expected certificate common name. Expected ALPN is checked. Keys use ECDSA P-256 generated by the OS-backed Go cryptographic random source. No static default password, plaintext outer data path, verification bypass option or custom cryptographic primitive exists. QUIC 0-RTT is disabled. Standard TLS/QUIC packet protection supplies connection-level replay protection; repeated legitimate application requests are not deduplicated across connections.

Treat possession of an allowed client certificate/key as authorization to every named server service. Per-client per-service ACLs, revocation and multi-tenant isolation are not implemented. Use a dedicated CA for each deployment/trust domain and restrict backend targets. A client supplies only an allowlisted service identifier and matching protocol; it cannot choose a remote IP/port. Configuration and all TLS material remain trusted operator input.

Sessions, per-flow queues, frame allocation, deadlines and server connection admission are bounded. TLS handshake admission is limited to 50 per second with a 50-token burst and concurrent session cap. QUIC cryptographic handshakes occur in the library before application-level admission, so this is not comprehensive pre-authentication DDoS protection. A network firewall/provider-level limit still needs deployment-specific review. No raw socket, TUN or admin privilege is required by the Go core.

Systemd runs a dedicated unprivileged account with protected filesystem/home/kernel, private devices/tmp, task/fd/memory limits and only `CAP_NET_BIND_SERVICE` for low ports. The installer journal and ownership data are root-owned and separate from service-writable runtime state. Installer subprocesses use argument arrays; there is no shell interpolation of remote/configured data. Existing SSH and firewall settings are never altered. Filesystem transactions are scoped to an explicit allowlist; symlinks are refused. This is not a formal security audit or a guarantee against a root attacker or concurrent privileged filesystem changes.

Logs contain operation errors/status, not certificate keys or payloads. Error strings can contain local paths. Diagnostics should be reviewed before publication. `.private`, `deployment-records`, live deployment configs, keys, certificates and captures are excluded from distribution; release packaging uses a file allowlist and never packages the workspace wholesale. Do not rely on `.gitignore` as a secret scanner.

Native port forwarding leaves other DNS, IPv4 and IPv6 traffic on existing OS routes. The optional engine has a separately tested isolated dual-stack TUN namespace and proxied DNS; only applications inside that namespace use its egress. Its fail-closed test does not establish a system-wide leak prevention policy. WireGuard site namespaces likewise have explicit peer/subnet routes and no physical underlay. See [engine/site lifecycle](engine-site.md). Plain native TLS/QUIC fingerprints and timing/length patterns are visible. Field acceptance on the supplied Iran–Turkey route failed; censorship bypass and active-probe resistance remain **Not Verified**.

Before production: run supported-toolchain `govulncheck ./...`, review the exact pinned dependencies and advisories, validate wrong CA/name/expired/revoked identity behavior, fuzz and race-test, perform sustained resource/DoS tests, and validate clean Linux installs, restart/outage behavior and the actual Iranian route. A successful static scan does not establish overall security. Old toolchains used for laboratory builds do not establish release eligibility.
