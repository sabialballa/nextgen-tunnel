# UDP pauses: rc3 investigation

Two separate issues were identified. The rc2 initiator duplicated encrypted WireGuard traffic into two independent REALITY/smux connections, but its listener had redundancy disabled. WireGuard learned the last engine UDP source as its return endpoint, so reverse traffic used one carrier. The rc3 listener now pins WireGuard to one connected local UDP socket and replicates replies to recently active carrier endpoints. WireGuard still authenticates packets and rejects replay; the relay does not decrypt user traffic.

The listener has four peer slots, a 30 second cache lifetime, queues of 64 datagrams per carrier, a 2048 byte datagram cap and 100 ms write deadlines. Only loopback WireGuard-shaped packets enter its cache. This shape check is not authentication of local processes; use dedicated hosts with trusted local users. The initiating relay continues to accept traffic only from its configured WireGuard socket. Both modes remain loopback-only, without a public forwarding service.

Real UDP regression tests verified that both carriers receive replies, WireGuard's endpoint remains fixed and malformed or oversized packets are rejected. Linux race/vet,24Python tests, real installation/rollback/crash recovery and the exact-binary vulnerability scan passed. The scan used the recorded official database snapshot and is not a security audit. See [race/vet](evidence/linux-race-rc3.txt), [Python](evidence/linux-python-rc3.txt), [installation](evidence/stack-installation-rc3.json), [core scan](evidence/security-core-rc3.json), [configuration regression](evidence/multiservice-rc3.json) and [profile generation](evidence/preparation-rc3.json).

A field header capture confirmed 662 inbound and 664 return datagrams per carrier on two carriers, with zero kernel capture drops. The WireGuard endpoint matched the owned relay socket. [Reverse-path evidence](evidence/reverse-fanout-rc3.json). This verifies the repaired reverse branch; it does not prove the entire route is free of stalls.

The two-carrier diagnostic still showed UDP deadline misses. Matching encrypted WireGuard header hashes between the endpoints' loopback sockets identified 7388 and 7382 unique emitted datagrams in a guarded 163.8 second window. All matched at the receiver. Some arrived substantially late: additional one-way delay relative to the median reached 519.6 ms and 793.3 ms. Subtracting the median removes a fixed clock offset; these are additional transport-path delays, not exact network-only one-way latency. Capture kernel drops and UDP receive/send buffer errors were zero. [Timing evidence](evidence/wg-delay-rc3.json).

Around the largest observed delay, established TCP connections stayed the same while retransmission counters increased: Iran 3 segments/837 bytes, Turkey 11 segments/9128 bytes. This is consistent with TCP loss recovery holding queued UDP frames behind missing TCP bytes. It does not identify a provider, middlebox or DPI mechanism, nor prove every pause has one cause. [Counter evidence](evidence/carrier-retrans-rc3.json).

Four independent carriers were then tested as a bounded mitigation. A short capture confirmed 662 inbound and 660 return datagrams on each of the four carriers, with zero capture drops. [Four-carrier proof](evidence/four-carrier-proof-rc3.json). All share the same physical route, and duplication approximately quadruples useful WireGuard traffic in each direction, plus framing/padding. This is not provider diversity and cannot guarantee delivery before a 500 ms deadline during a shared stall.

The unchanged acceptance limits are TCP without timeouts/reconnections, UDP deadline loss at most 0.5%, maximum UDP failure burst 3, no corrupted payloads, stable engine PID and 3600 real seconds on both nodes. The final values are in [the hour report](evidence/hour-rc3.json). More copies must not be described as a successful fix if those criteria fail. The rc2 and preliminary rc3 failed observations remain preserved. No GitHub publication is part of this work.
